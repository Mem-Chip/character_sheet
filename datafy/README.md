# 数据化工作包（给 AI 代理用的说明）

把 D&D 2024 的规则原文写成规则引擎能执行的 JSON。你要做的事：**逐条读任务 → 写答案文件 → 跑检查命令 → 没过就改**，全部做完后收集、检查、跑测试。

所有命令都在**仓库根目录**运行（这个文件夹的上一级）。需要 Node 22+，第一次先 `npm install`。

## 一、这里有什么

| 文件夹 | 内容 | 要做的 |
|---|---|---|
| `batch-w2-spells/` | 2024 玩家手册的法术，384 条，分 44 批（`batches.json`） | **全部要做** |
| `batch-w1-features/` | 职业 / 子职特性、专长、可选特性、种族，545 条 | 已经做完了，只剩 `retry.md` 里列的 13 条要重做 / 改进 |

每个文件夹里：

- `spec.md` —— **写法说明，开工前完整读一遍**。里面有格式、表达式能用的名字、每个时机能用什么、引擎的执行细节、资源池怎么声明、什么时候该跳过。
- `examples.json` —— 手写的标准答案（几十条，都有场景测试）。照着它们的风格和粒度写。
- `tasks/<题号>.md` —— 一条任务：原文、职业表、可以花的资源、接口要求。（`.ctx.json` 是给检查程序用的，不用看。）
- `answers/<题号>.json` —— 你写的答案放这里。
- `batches.json` —— 分批：同一批里是同一组（同一个职业、同一环法术），做的时候一批一批来，保持写法一致。
- `manifest.json` —— 题号 → 条目键的对照。

## 二、做一条任务

1. 读 `tasks/<题号>.md`。
2. 写答案到 `answers/<题号>.json`。两种写法：
   - 一个条目（格式见 `spec.md`，例子见 `examples.json`）；
   - 或者跳过：`{ "skip": "一句话原因" }`。纯静态的（人物卡已经算了的熟练、加值）、纯叙事的、只是目录 / 授予别的条目的，都应该跳过。
3. 检查：
   ```bash
   npx tsx tools/factory/batch.ts lint datafy/batch-w2-spells S001
   ```
   （特性那边把目录换成 `datafy/batch-w1-features`，题号是 `F` 开头的。）
   输出 `✓ 通过` 或 `✓ 跳过` 就好了；`✗` 会列出问题，改完再跑，**最多改 4 轮**，还不过就改成 `automation: "partial"` / `"manual"` 或者跳过。

## 三、原则

- **宁可 skip、partial、manual，也不要写错**。引擎做不到的部分写进 `text` 说明，标成部分自动化。
- 原文里**隐含的自动规则**也要写出来（比如「攻击敌人时狂暴自动延长」）。
- **同一批保持一致**：资源 id、效应名、标签名在同一个职业 / 同一组法术里要一样。
- 需要新的次数池（「每次长休一次」）才在答案顶层写 `resources` 声明（见 `spec.md`）；任务里列了的资源直接用，不要重复声明。
- 法术的升环：伤害骰写成 `(2 + slot.level)d6` 这种，跟着原文的「每高一环」算；戏法按角色等级增长见 `spec.md`。
- **只写 `answers/` 里的文件**。不要改仓库里的其他文件（引擎代码、手写数据、测试）。觉得引擎缺了某种能力，记到 `datafy/notes.md` 里（写清楚是哪条、缺什么）。

## 四、收集

一批（或者全部）做完后：

```bash
npx tsx tools/factory/batch.ts collect datafy/batch-w2-spells
```

它会把每份答案再检查一遍，并在一场模拟战斗里真的跑一遍（用掉所有动作、被攻击、做豁免、过几个回合），然后：

- 通过的写进 `data/dyn/ai/spells.json`（特性是 `data/dyn/ai/features.json`），标「AI 生成、未审」；
- 答案里声明的新资源池写进 `data/abilities-2024.json`；
- 没过的列在 `<目录>/failures.json`，带着问题 —— **照着问题改答案，再 collect**，直到没有失败或者只剩确实写不了的（那些改成 manual 或 skip）。

collect 可以反复跑，每次都会按 answers 里的最新内容重新生成。

## 五、检查（做完之后自己审一遍）

检查程序只保证「格式对、跑起来不出错」，不保证「写得对」。每一批做完，回头对照原文抽查，重点看：

- 数字：伤害骰、DC、射程、范围大小、持续时间、次数；
- 豁免用的属性、伤害类型、成功时减半还是无效；
- 升环、戏法随等级增长；专注；仪式；
- 目标：单体 / 多个 / 范围，敌我；
- `automation` 标得诚实：手动处理的部分写清楚了吗。

发现的问题直接改答案再 collect。审完在 `datafy/review.md` 里写几行：查了哪些、改了什么、还有哪些拿不准。

## 六、最后

```bash
npm test
npm run check:data
```

- `npm test` 里只有「角色快照」测试失败、而且差别只是多了新的资源池（`_resources` / `_derived.resources` 里多出来的条目）的话，这是预期的：跑 `npm run snapshots` 更新快照，再跑一遍 `npm test`。
- 其他测试失败：不要去改测试，把失败信息记到 `datafy/notes.md`。

做完之后汇报：每个文件夹写了多少、跳过多少、没过多少，`notes.md` 和 `review.md` 里的要点。不用提交 git，人会看过之后再提交。
